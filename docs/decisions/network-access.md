# Network access opt-in

## Context

TermForge controls SSH sessions, files and credentials, so reaching it from another device is equivalent to having the user's shell on every saved server. The specification keeps loopback-only binding as the default and allows remote network access only as an explicit opt-in with authentication (`PROJECT_SPEC.md` sections 1 and 11). The launch link used locally (`local-browser-session.md`) cannot work for other devices: it is delivered by opening the local browser.

## Decision

- **Explicit, separate configuration.** Network access mode is enabled only by `NetworkAccess:Enabled=true`. Without it the existing loopback binding validation is unchanged and any non-loopback binding stops the process. Enabling it does not bind anything by itself; the user adds a Kestrel endpoint.
- **Refuse to start instead of degrading.** With network access mode enabled the startup filter refuses to start, before Kestrel listens, when there is no valid password hash (even on loopback-only bindings), when `NetworkAccess:AllowedHosts` is empty or malformed, when a limit is not positive, or when a network binding is plain HTTP without explicit consent.
- **HTTPS is required; plain HTTP is a loud, explicit opt-out.** A password and a session cookie sent over plain HTTP on a LAN or public Wi-Fi can be sniffed and replayed, which gives full shell access. Therefore every non-loopback binding must use `https://`. `NetworkAccess:AllowInsecureHttp=true` exists for isolated networks or for a TLS-terminating proxy the user controls; it logs a `Critical` "INSECURE" message per plain HTTP binding on every start and the sign-in form warns when opened over HTTP from a non-loopback host. A warning alone was rejected as the default because it is easy to miss on a background process; refusing HTTPS-less setups entirely was rejected because it blocks reasonable proxy setups. TermForge does not generate certificates.
- **Single password stored as a strong hash in configuration.** `TermForge --hash-password` prints `pbkdf2-sha256$<iterations>$<salt>$<hash>` (PBKDF2-HMAC-SHA256, 600 000 iterations, 16-byte random salt, 32-byte hash, minimum length 12). Hashes with fewer than 100 000 iterations are rejected. `Rfc2898DeriveBytes.Pbkdf2` was chosen over ASP.NET Core Identity's `PasswordHasher` to avoid a new package for one function and to keep the iteration count visible and enforceable. The OS credential store was not used: the hash is not a secret that must be recoverable, configuration works on headless machines, and environment variables work in containers.
- **Rate limiting and lockout in the sign-in handler.** Each attempt is reserved against the client IP address (default 5) and a global counter (default 20) before PBKDF2 runs, so concurrent requests cannot exceed the limit and locked-out requests cost no CPU. Reaching a limit locks sign-in for `LockoutMinutes` (default 15), even for the correct password, answered with `429` and `Retry-After`. Success resets the counters. The ASP.NET Core rate limiter was not used: it limits request rate, not failed attempts, and has no lockout.
- **Same session mechanism for both ways in.** Password sign-in creates the same kind of browser session as the launch link: `termforge_session` cookie (`HttpOnly`, `SameSite=Strict`, `Secure` over HTTPS) plus the synchronizer CSRF token. The session store now holds several sessions (at most 32, oldest dropped) looked up by the SHA-256 of the token; password sessions have an absolute lifetime (default 12 hours). Sign-out removes the session. All existing protections (session for every `/api` request and WebSocket, CSRF, exact `Origin`, `Sec-Fetch-Site`) apply unchanged, so every feature endpoint, including the realtime channel, terminals, file browsing and diagnostics, is protected without opting in.
- **Host allow-list extended, not replaced.** Loopback hosts stay accepted; `NetworkAccess:AllowedHosts` adds exact host names or IP addresses (no wildcards, ports or schemes), compared case-insensitively. DNS rebinding protection therefore still holds for every other name.
- **Sign-in UI in the SPA.** On `401` the SPA asks `GET /api/session/login` and shows a password form when sign-in is enabled. The SPA shell and assets stay public; they contain no secrets.

## Consequences

- Default installations behave exactly as before.
- Users must provide a certificate trusted by their devices for the recommended setup.
- An attacker on the network can trigger the global lockout and block password sign-in for its duration; the local launch link still works. Counters and sessions are in memory and reset on restart.
- Single user only: there are no accounts, roles or second factor. Multi-user support is out of scope.
- Reverse proxies are supported only as transparent TLS terminators that keep `Host` and `Origin`; forwarded headers are not trusted, so all clients behind a proxy share one per-client counter.
